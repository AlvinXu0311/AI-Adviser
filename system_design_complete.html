🎯 Key Architecture Decisions

  • Database-First Strategy: SQLite provides authoritative, structured data (instructor, credits, schedules). RAG (ChromaDB) supplements with detailed descriptions from PDFs.
  • ReAct Pattern: LangChain agent uses Reasoning + Acting loop. Agent autonomously decides which tools to use and when, enabling complex multi-step queries.
  • Intent Classification: 2-layer validation prevents wasted LLM calls. Layer 1: basic sanity check. Layer 2: LLM-powered intent classification with conversation context.
  • Unified Search with Retry: All search tools share common logic: try DB → try RAG → retry with query variations (up to 3 attempts). Prevents "not found" errors.
  • Session-based Isolation: Each browser session gets unique session_id. Student context (transcript) and conversation history isolated per session, preventing data leakage.
  • Redis for State: Conversation history and student context cached in Redis with 24h TTL. Enables fast retrieval and automatic cleanup.
  • Streaming Responses: SSE (Server-Sent Events) for real-time streaming. Frontend receives chunks as LLM generates them, improving perceived performance.
  • Course-Aware Vector Search: ChromaDB search boosts results that match course codes in metadata (0.3-0.5 score boost). Solves cross-listed course problem (e.g., "ECE 577" finds "DS/ECE 577").
  • Semantic Chunking: PDFs chunked by course boundaries (regex pattern matching). Each chunk = complete course info (code + title + description), improving retrieval accuracy.
  • Dynamic Program Loading: Agent prompt includes program list fetched from database at runtime. New programs auto-detected without code changes.
  • Multi-turn Context: Last 6 messages (3 turns) sent to intent classifier. Last 20 messages sent to adviser agent. Enables follow-up questions like "tell me more" or "what about MSBA?"
  • Tool Hierarchy: smart_course_search (primary for courses) → program_search (primary for programs) → semantic_search (fallback). Ensures most accurate tool selected first.

📊 Detailed Request Processing Steps

  1. User Authentication: Microsoft SSO validates @wpi.edu email. MSAL library manages OAuth 2.0 flow and token refresh.
  2. Session Initialization: Frontend generates session_id (UUID) on first message, stored in sessionStorage. Sent with every request.
  3. Message Submission: User types message → Frontend calls chatService.sendMessage() → POST /api/chat with {message, session_id, topic_id}
  4. Layer 1 Validation: Basic sanity check (not empty, contains alphanumeric). Rejects garbage input immediately.
  5. Memory Retrieval: Redis fetch: get conversation history (message_store:{session_id}). Last 6 messages retrieved for intent classification.
  6. Layer 2 Intent Classification: Intent Agent (Gemini Flash) analyzes message + conversation history → {intent, confidence, is_academic, requires_transcript}. Rejects if not academic or confidence < 0.2.
  7. Context Loading: If transcript uploaded, Context Manager retrieves student data from Redis (student name, GPA, completed courses).
  8. Agent Invocation: Adviser Agent (Gemini Pro) receives: query + conversation history (20 msgs) + student context + topic guidance.
  9. ReAct Loop: Agent generates Thought → decides Action (tool) → executes Tool → receives Observation → repeats (max 10 iterations).
  10. Tool Execution: Each tool uses unified_search: DB query (attempt 1) → RAG search (attempt 2) → keyword variations (attempt 3). Returns best match or empty.
  11. Response Generation: After sufficient tool use, agent generates Final Answer. LLM streams response in chunks.
  12. Memory Storage: User message and AI response saved to Redis (message_store:{session_id}). TTL refreshed to 24h.
  13. Response Streaming: Backend yields SSE events (data: {type, content}). Frontend parses and displays chunks in real-time.
  14. Session Cleanup: Redis auto-expires sessions after 24h inactivity. Context Manager evicts oldest 10% if > 1000 active sessions (LRU policy).

⚡ Performance & Scalability Considerations

Response Times

  • Intent Classification: 1-2 seconds (Gemini Flash, timeout: 6s)
  • Simple Query: 3-5 seconds (1-2 tool uses)
  • Complex Query: 8-15 seconds (3-5 tool uses)
  • Degree Progress: 5-10 seconds (DB comparison)
  • PDF Upload: 2-5 seconds (extraction + storage)

Caching Strategy

  • Conversation History: Redis (24h TTL, max 100 msgs/session)
  • Student Context: Redis (24h TTL, touch on access)
  • Vector Embeddings: ChromaDB persistent storage (no re-embedding)
  • Database Queries: No caching (data changes infrequently)
  • Session Cleanup: Auto-expiration via Redis TTL

Scalability Limits

  • Max Concurrent Sessions: 1000 (Context Manager limit)
  • Redis Memory: ~100MB for 1000 sessions
  • ChromaDB Size: ~50MB (4 PDFs, 500 chunks)
  • SQLite DB Size: ~10MB (programs, courses, requirements)
  • Gemini API Rate Limit: 60 requests/minute (free tier)

Optimization Techniques

  • Streaming Responses: Reduces perceived latency
  • DB-First Search: Avoids slow vector search when possible
  • Query Retry Logic: 3 attempts with variations (improves recall)
  • Batch Embedding: 50 documents at a time (prevents memory issues)
  • Course-Aware Ranking: Boosts relevant results (improves precision)
  • LRU Eviction: Oldest 10% evicted when limit reached

🔒 Security & Privacy Measures

Authentication & Authorization

  • Microsoft SSO: Only @wpi.edu emails allowed
  • OAuth 2.0: Industry-standard auth protocol
  • Token Refresh: MSAL auto-refreshes access tokens
  • Session Isolation: Each session has unique ID
  • No Persistent User DB: No user data stored long-term

Data Privacy

  • Session-Based Storage: Data isolated per session_id
  • Auto-Expiration: All data deleted after 24h inactivity
  • No Cross-Session Leakage: Context Manager enforces isolation
  • Transcript Data: Stored in memory (Redis), not disk
  • No Logging of PII: Student names/IDs not logged

Network Security

  • CORS: Only allowed origins (localhost + production)
  • Nginx Proxy: Hides backend port from public
  • HTTPS Ready: SSL/TLS support (production)
  • Rate Limiting: Gemini API limits (60 req/min)
  • Input Validation: Pydantic schemas + sanity checks

Container Security

  • Alpine Base Images: Minimal attack surface
  • Bridge Network: Containers isolated from host
  • No Root User: Non-privileged container users
  • Health Checks: Automatic restart on failure
  • Environment Variables: Secrets managed via .env
